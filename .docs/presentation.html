The brief we were given

Build a QA test
automation tool.

Writing and maintaining browser tests is slow, manual, and goes stale the moment the product changes. The QA loop is where velocity goes to die.

What if QA was a conversation, not a codebase?

How we approached it

Architecture first.
Then parallel.

  • 1Discussed the high-level solution and architecture first — we agreed on the shape of the system before writing a line.
  • 2Came up with a high-level plan — 3 loosely coupled phases that three people could build in parallel from hour zero.
  • 3Divide and conquer — we worked in parallel and finally merged it all together.

How it got merged

No merge hell — by design

  • →Contract-first API. The basic API layer and contract were written before logic — so the frontend never waited on the backend.
  • →HITL placeholder for Agent 2. Before the sandbox landed, a human-in-the-loop stub let the orchestration run end-to-end.
  • →Defined seams. Because the boundaries were agreed up front, the final merge was fast and conflict-free.

The agent architecture

QA orchestration, end to end

Agent 2 — deep dive · the Claude workspace

An agent, let loose in a real desktop

Driver
Claude Computer Use — clicks, types, screenshots a live browser
Model
Haiku for recon — fast, no code generation
Budget
~3 min wall-clock · ≤10 tool calls
Speed levers
token-efficient tools beta · only N recent images in context
Output
a findings report + an event log — documentation only

The workspace contract

▸Writes only to a single output workspace — bind-mounted back to the host
▸A findings report — summary · surfaces · behaviours · coverage · risks
▸An event log — one line per meaningful action
✕Forbidden: source code, tests, fixtures. Observe & document — don't build.
Soft success: if the sandbox hits its deadline but the findings report was already written, we treat it as a success and hand the artefacts to Agent 3 — a hung tool call at the end shouldn't fail the whole run.
Agent 2 — deep dive · the sandbox setup

One image, an isolated container per task

qa-sandbox containerbase: Anthropic Computer Use image
Chromium + X11 desktop — a real, headed browser
pytest + playwright — preinstalled, so bundles run with zero setup
entrypoint dispatches on TASK_KIND — exploration vs execution
/task volume, bind-mounted — artefacts flow straight back to the API
noVNC on :6080 — the live view you watch in the UI
Isolation
Fresh container per task · memory + CPU limits · scoped network
Concurrency
Capped by MAX_CONCURRENT_TASKS — the spawner queues the rest
Reused by
Agent 2 (explore) · Agent 4 (author) · execution (run pytest)
Live view
noVNC URL is HMAC-signed by the sandbox service
Why a whole desktop? A QA agent has to see and act on the product the way a person does — so we gave it a person's environment: a screen, a browser, and a keyboard, sealed inside a disposable container.
